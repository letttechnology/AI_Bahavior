To handle irregular verbs in *any* language within a pure rules engine—without resorting to flat lookup tables of fully conjugated words—you have to shift from matching **strings** to matching **lexical features and stem paradigms**.

In linguistics and compiler design, this is handled by treating irregularity not as a random mistake, but as a specific **sub-rule** with higher priority than the default rule.

Here is the practical engineering blueprint for a language-agnostic morphological rules engine.

---

### The Architecture: Stem + Paradigm + Feature Matching

A cross-language rules engine requires two things to process any verb:

1. **The Lexeme Object:** The input word cannot just be a raw string. It must be an object carrying its grammatical root and its **Paradigm Class**.
2. **The Rule Pipeline (Ordered by Salience):** Highly specific paradigm rules execute first. The catch-all default rule executes last.

```
[Input Lexeme + Features] ➔ [Paradigm Rules (High Priority)] ➔ [Default Rule (Low Priority)] ➔ Output

```

### Step 1: Define the Lexeme Properties

Instead of hardcoding "overtake $\rightarrow$ overtook", your lexicon stores the root and tags it with a paradigm class.

* **English Example:** `{ root: "take", paradigm: "strong_ablaut_a_o" }`
* **Spanish Example:** `{ root: "dormir", paradigm: "stem_change_o_ue" }`
* **Regular Example:** `{ root: "walk", paradigm: "regular" }`

*Note: You aren't hardcoding the final conjugated word here. You are categorizing the word by how its spelling behaves.*

### Step 2: Implement the Engine Rules (Pattern Matching)

Your rules engine evaluates the `paradigm` attribute and the target grammatical `features` (passed from your parsing codes like `V-AAI3S`).

#### Rule Set A: Specific Paradigm Mutations (High Priority)

You write rules based on the *behavioral classes* of the target language.

```java
// Rule 1: English Strong Ablaut (take -> took, shake -> shook)
IF paradigm == "strong_ablaut_a_o" AND tense == PAST:
    RETURN replace_vowel(root, "a", "oo") 

// Rule 2: Spanish O->UE Stem Change (dormir -> duermo)
IF paradigm == "stem_change_o_ue" AND person == 1 AND number == SG:
    RETURN replace_vowel(root, "o", "ue") + "o"

// Rule 3: Prefix Reduplication (Greek Perfect Tense logic)
IF language == GREEK AND tense == PERFECT:
    RETURN initial_consonant(root) + "ε" + root + perfect_suffix

```

#### Rule Set B: The Default Fallback (Lowest Priority)

If the lexeme's paradigm matches "regular", or if no specific paradigm rule triggers, the engine falls back to the standard algorithmic rule for that language.

```java
// Default English Past Tense
IF language == ENGLISH AND tense == PAST:
    RETURN root + "ed"

// Default Spanish Present Tense (for -ir verbs)
IF language == SPANISH AND tense == PRESENT AND conjugation == "ir":
    RETURN strip_ending(root) + "o"

```

---

### Why This Works Across Any Language

By modeling the engine this way, you solve the "irregularity" problem programmatically because most irregular verbs actually share systemic structural patterns (allomorphy):

1. **Vowel Mutations (Ablaut/Umlaut):** Common in Germanic languages (English, German). The rule engine handles this via regex or string manipulation functions executed *inside* the rule (e.g., `sing` $\rightarrow$ `sang`, `drink` $\rightarrow$ `drank` both share a `strong_i_a` paradigm rule).
2. **Stem Infixes/Suffixes:** Common in Romance languages. The engine alters the root stem *before* appending the person/number suffixes.
3. **Suppletion (Complete Word Changes):** For absolute outliers (like "be/was" or "go/went"), the paradigm class is literally `suppletive`. The rule for this specific paradigm is a direct swap: `IF paradigm == "suppletive_go" AND tense == PAST: RETURN "went"`.

### Summary of Practical Reasoning

If you want a pure rules engine:

* **Don't** write rules for individual words (`if word == "overtake"`).
* **Don't** assume a single rule (`root + "ed"`) covers a language.
* **Do** group words into **Paradigms**, and write your rules to manipulate strings based on those paradigm groups.

This keeps your Java layer purely algorithmic. The rules engine handles the linguistic transformations, and your database or dictionary layer only needs to store a single attribute pointing the word to its correct rule group.

### The Real Solution: An Ordered Regex Rules Engine

To handle irregular verbs programmatically in *any* language without a massive database of fully formed words, the rules engine should use an **Ordered List of Pattern Transformations** (Regex).

Instead of checking if a word *is* irregular, the engine checks if the word *ends with* or *contains* an irregular phonetic pattern.

When the Greek morph code `V-AAI3S` resolves to `Tense=PAST`, the engine passes the English gloss string through a localized pipeline of regex rules. The first rule that matches executes its transformation and breaks the loop.

#### The Past Tense Rule Pipeline (Executed in Order)

| Priority | Pattern Match (Regex) | Replacement | Examples Handled |
| --- | --- | --- | --- |
| **1 (Phrasal)** | `^(.+)lay(\s.+)$` | `$1laid$2` | "lay hold of" $\rightarrow$ "laid hold of" |
| **2 (Suffix)** | `^(.*)take$` | `$1took` | "take" $\rightarrow$ "took", "overtake" $\rightarrow$ "overtook" |
| **3 (Suffix)** | `^(.*)come$` | `$1came` | "come" $\rightarrow$ "came", "overcome" $\rightarrow$ "overcame" |
| **4 (Suffix)** | `^(.*)bind$` | `$1bound` | "bind" $\rightarrow$ "bound", "unbind" $\rightarrow$ "unbound" |
| **5 (Default)** | `^(.*)$` | `$1ed` | "walk" $\rightarrow$ "walked", "seize" $\rightarrow$ "seized" |

#### Why this is the correct architecture for Greek-to-English:

1. **Zero Prefix Curation:** The `^(.*)take$` rule automatically catches *take*, *overtake*, *undertake*, *partake*, and *mistake* using a single line of code.
2. **Decoupled from Lexicon Changes:** If a user changes the gloss of G2638 from "overtake" to "lay hold of", Rule 2 stops matching, but Rule 1 instantly catches it. The engine remains completely dynamic and never outputs "lay hold ofed".
3. **Language Agnostic:** This exact same engine structure works for Spanish, German, or Greek. You just swap out the regex pipeline file based on the target language attribute.

### How to Implement It in Java

Instead of loading 200 fully conjugated words, you load a small array of rule objects at startup.

```java
public class InflectionRule {
    private Pattern pattern;
    private String replacement;

    public InflectionRule(String regex, String replacement) {
        this.pattern = Pattern.compile(regex, Pattern.CASE_INSENSITIVE);
        this.replacement = replacement;
    }

    public String apply(String input) {
        Matcher matcher = pattern.matcher(input);
        if (matcher.matches()) {
            return matcher.replaceAll(replacement);
        }
        return null; // No match, move to next rule
    }
}

```

The engine loops through your `List<InflectionRule> pastTenseRules`. The moment a rule returns a non-null string, that is your conjugated verb. The very last rule in the list is your fallback: `^.*$ -> $0ed`.

This is a true rules engine. It keeps the data out of the database, handles the erratic nature of English gloss variations, and scales perfectly.
