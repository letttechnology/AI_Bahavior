CREATE TABLE IF NOT EXISTS lexeme_sense (
    id          BIGSERIAL PRIMARY KEY,
    lexeme_id   INTEGER NOT NULL REFERENCES lexeme(id) ON DELETE CASCADE,

**Columns:**
| Column | Purpose |
|--------|---------|
| `lexeme_id` | FK to the lexeme/cluster |
| `sense_index` | 0 = NT primary sense, 1+ = secondary senses |
| `gloss` | The English gloss text for this sense |
| `sense_type` | `nt_primary` (index 0), `secondary` (index 1+), or `classical_only` (not used today) |
| `nt_attested` | Always `true` — all senses come from NT-focused corpus data |

**Who populates it:**

**Ordering logic:**

3. All rows get `nt_attested = true`

5. Stale `token_sense_override` rows (pointing at nonexistent sense_index values) are cleaned up

There is **no explicit ordering column** — the ordering is strictly `sense_index` (0 = primary/always first, 1+ = secondary). There is no `display_order` or `sort_order`.

### 5. The COALESCE in `InflectionEngineService.fetchAllTokens()`

**Complete SQL** (lines 876-895):
```sql
SELECT
  vw.id AS verse_word_id, vw.verse_id, vw.lexeme_id, vw.pos_code, vw.morph_key,
  vw.tense, vw.voice, vw.mood, vw.person, vw.number,
  vw.gender, vw.grammatical_case, vw.english_gloss,
  vw.dep_head_id, vw.dep_relation,
  l.strongs_id, l.is_stative, l.is_polysemous,

  COALESCE(ls_ai.gloss, ls.gloss, m.short_gloss) AS resolved_gloss,
  COALESCE(tso.sense_index, 0) AS sense_index,
  (tso.sense_index IS NOT NULL) AS has_ai_override,
  m.short_gloss AS corpus_gloss

FROM verse_word vw
LEFT JOIN lexeme l ON vw.lexeme_id = l.id
LEFT JOIN lexeme_meaning m ON m.lexeme_id = l.id AND m.source = 'corpus'
LEFT JOIN lexeme_sense ls ON ls.lexeme_id = l.id AND ls.sense_index = 0
LEFT JOIN token_sense_override tso ON tso.verse_word_id = vw.id
LEFT JOIN lexeme_sense ls_ai ON ls_ai.lexeme_id = l.id
  AND ls_ai.sense_index = tso.sense_index
ORDER BY vw.id
```

**COALESCE priority for `resolved_gloss`:**
1. `ls_ai.gloss` — lexeme_sense entry joined via `token_sense_override.sense_index` (the AI-selected sense gloss). **This is the only way `token_sense_override` participates.**
2. `ls.gloss` — lexeme_sense where `sense_index = 0` (the default/primary sense)
3. `m.short_gloss` — lexeme_meaning.corpus raw corpus gloss (fallback)

**Token_sense_override fit:**
- `tso.sense_index` is used to select which `lexeme_sense` row to use via the `ls_ai` join
- `tso.sense_index` is also returned directly as `sense_index` (COALESCE to 0)
- `tso.sense_index IS NOT NULL` → `has_ai_override` boolean flag

**What would need to change to make it select `sense_index` per token?**
This is a **build-time** query. For **read-time** sense_index per token, you would need to:

1. **Add `sense_index` to `gloss_set_entry` in the upsert** — currently `InflectionEngineService.upsertBatch()` (lines 950-968) does NOT populate the `sense_index` column on `gloss_set_entry`. The V19 migration added the column, but the batch write ignores it. The `ON CONFLICT DO UPDATE SET` doesn't include `sense_index`.
2. **Propagate `gloss_set_entry.sense_index` through to `TokenDto`** — currently `GlossChainService.GlossResult` includes `senseIndex` (line 74), and the SQL reads `gse.sense_index` (line 144), but `TokenDto` has no `senseIndex` field.
3. **Alternatively**, add a `sense_index` column to `verse_word` itself for direct per-token storage.

### 6. Does `verse_word.sense_index` Exist?

**No.** The `VerseWord` entity (`D:\workspace-vscode\interlinear-bible-api\src\main\java\com\interlinear\bible\entity\VerseWord.java` lines 1-183) has **no `senseIndex` field** and there is no `sense_index` column on the `verse_word` table (verified across all migration files).

**Where `sense_index` IS stored in the DB:**

| Table | Column | Purpose |
|-------|--------|---------|
| `lexeme_sense` | `sense_index` | The sense position within a lexeme (0=primary, 1+=secondary) |
| `token_sense_override` | `sense_index` | The AI-selected or human-reviewed sense index for a specific token |
| `gloss_set_entry` | `sense_index` | The precomputed sense index for the cache entry (V19, not populated by the current code) |

**What would be needed for a `verse_word.sense_index` column:**
- A new Flyway migration (e.g., `V49`) adding `ALTER TABLE verse_word ADD COLUMN sense_index SMALLINT;`
- A backfill query to populate it from `token_sense_override.sense_index`
- A mapping on `VerseWord.java` (`@Column(name = "sense_index") private Short senseIndex;`)
- An update to `TokenDto` to expose it
- An update to the read path to propagate it

### Summary: The Current Flow

```
BUILD TIME (regenerateAllGlosses / InflectionEngineService)
  fetchAllTokens():
    COALESCE(ls_ai.gloss, ls.gloss, m.short_gloss) = resolved_gloss
    - ls_ai.gloss comes from lexeme_sense[tso.sense_index] if token_sense_override exists
    - ls.gloss is lexeme_sense[sense_index=0] (default primary sense)
    - m.short_gloss is raw corpus gloss (fallback)
    → result written to gloss_set_entry (ignoring sense_index column)

READ TIME (resolveBatch / GlossChainService)
  2.5 → contextual_gloss (only for 13 polysemous words)
  3   → gloss_set_entry (precomputed cache)
  3b  → gloss_set_entry (English fallback)
  4   → cluster_gloss_rule
  5a-e → fallback cascade
  1-2 → resolveUserOverlays (merged on top)
  
  token_sense_override is NEVER consulted at read time.
  lexeme_sense is NEVER consulted at read time.
```
