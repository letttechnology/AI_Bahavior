My input — and it resolves the cost-vs-separation tension, because the choice isn't actually binary.

## Separate *logically*, share *physically* — for now

The thing the #186 split bought you is a **logical** boundary: Reader owns no word detail, Lexis owns no passages, and they talk over HTTP (token id → Lexis — exactly what #210 just locked in). That boundary is what keeps the codebase from re-tangling into the monolith it came from. It is **not** the same thing as two database *servers*.

So:
- **Keep two databases** (`reader_db`, `lexis_db`) — but **on one Postgres instance**, with **separate roles/credentials**.
- **Defer two instances** until load or reliability actually demands it.

## Why this is the right cut

**The expensive coupling is in code, not infrastructure.** If the services never share a connection or join across each other's tables — and they don't; they call over HTTP — then moving from one instance to two later is a *connection-string change*, not a migration. If instead you collapse them into shared schemas and start joining freely, splitting later is a painful rewrite. Protect the cheap-to-keep boundary now; defer the costly physical split.

**Cost: you're likely conflating "database" with "bill."** On every managed Postgres (RDS, Cloud SQL, Neon, Supabase), you pay per **instance/compute** — multiple logical databases on one instance are free. So "two DBs" costs essentially nothing extra. Only "two **instances**" doubles the baseline. You can have full logical separation at one-instance cost today.

**Reasons to keep them logically separate even while cheap:**
- **PII boundary** — Reader holds user accounts, OAuth, email. Lexis (lexicon + Ask-AI chat) should not have credentials to those tables. Separate roles enforce least privilege; one shared DB role doesn't.
- **Migration isolation** — a Lexis schema migration shouldn't lock tables Reader is serving passages from.
- **Different growth curves** — corpus/lexicon is static reference data; Ask-AI chat (#192) grows unbounded. You don't want chat volume sitting in the same blast radius as passage serving.

## When to actually split to two instances

A concrete trigger, not a vibe:
- Ask-AI / chat write volume on Lexis starts affecting Reader's passage-serving latency, **or**
- you need to scale the two independently (Reader read-heavy, Lexis AI-heavy), **or**
- compliance forces hard PII isolation.

Until one of those is real, two instances is over-provisioning.

## One rule that keeps the door open for free

**No cross-database joins, ever — services communicate only over HTTP.** That's already true (token id → Lexis). Honor it and the eventual one-instance→two-instance move stays a config change. Break it once and you've quietly rebuilt the monolith.

Net: you don't have to choose between cheap and separated. One instance, two logical DBs, separate roles, HTTP-only between them — cheap today, splittable tomorrow without a rewrite.
